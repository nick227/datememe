## Deviations from Defaults

- **Expo instead of Vite/React** for the frontend, per explicit instruction. `apps/mobile` replaces `apps/web`; no web app exists in this repo.
- **`AuthResponse` includes a `token` field in the body**, not just `Set-Cookie` — native apps can't rely on a cookie jar, so the mobile SDK client reads this and stores it via `expo-secure-store`, injecting it as a Bearer header on every request (`packages/sdk/src/client.ts`'s `getToken` override, which the template already anticipated).
- **v3 pivot — swipe/match replaces browse-and-message-freely.** Mid-session, additional mockups (`art/match.png`, `art/profile.png`, `art/home.png`) surfaced a different direction than the original requirements/schema docs: Like/Pass swiping with a mutual-match gate, a percentage compatibility score + heuristic "insight" callouts, a short bio, and a small photo gallery. This was confirmed with the user and both docs were updated (schema doc v3, requirements doc v2) before implementing — see those docs' changelogs for the full reasoning. `Conversation.status` now defaults to `ACCEPTED` (a match already is the consent step); the old `POST /conversations` (message-anyone) endpoint no longer exists, replaced by `POST /swipes`.
- **List builder has no drag-to-reorder** — picked items are ranked by pick order; removing and re-adding is the only way to reorder in this pass. The `art/screen-idea.png` mockup implies drag reordering (the "≡" handle); simplified for time.
- **Swipe interaction is button-taps (Pass/Like), not a gesture-driven card stack** — functionally equivalent, no `react-native-deck-swiper`-style physics/animation.
- **`pnpm test:generate` / `pnpm docs:generate` / `pnpm pages:generate` scripts were not copied** — they don't apply cleanly to an Expo frontend (`pages:generate` is Vite-specific) and weren't essential to standing the stack up. `apps/server` has one hand-written test file (`pagination.test.ts`) instead of spec-generated stubs.
- **Root `tsconfig.base.json`** is used by `packages/*` and `apps/server`; `apps/mobile` uses Expo's own `expo/tsconfig.base` instead, which is the correct/expected setup for an Expo app and not a deviation from anything — just worth noting they're different configs.
- **`pnpm.overrides` pins `react`/`react-dom` to `19.2.3`** at the workspace root — `packages/sdk`'s peer dependency on React was resolving a second copy under its own `node_modules` (`expo-doctor` flagged this; two React copies is a real runtime crash risk in React Native, not cosmetic).

**Bugs found and fixed via this live testing** (none of these were caught by typecheck/lint — only real requests surfaced them):
1. `serializeConversation` applied the premium photo-gate to *every* participant including the viewer's own profile — a free-tier user couldn't see their own photo in their own conversation list. Fixed by revealing a participant's photo when `participant.id === viewerProfileId`, regardless of tier (`MessagingService.ts`).
2. `EntitySubmission.suggestedMatch` was declared as a non-nullable `$ref` in the OpenAPI spec; `fast-json-stringify` silently coerced an actual `null` value into `{}` instead of erroring or passing it through. Fixed with the `nullable: true` + `allOf` wrapper pattern (matches how `Subscription`'s nullable field was already handled) and added to `required` since it's always present as either an entity or `null`.
3. The seed script wrote `ListItem` rows directly, bypassing `ListService`'s transaction that maintains `Entity.usageCount` — so autocomplete ranking looked wrong for seeded data (everything at 0) even though the real app-code path was correct. Fixed the seed script to increment on first creation (idempotent on re-seed) and backfilled existing rows with `UPDATE Entity SET usageCount = (SELECT COUNT(*) FROM ListItem ...)`.

**Known non-bug edge case, not fixed:** a pending entity submitted into a category with `requiredTags` (e.g. "Top 90s Bands") won't reappear in that category's *search results* even for its own submitter, because new submissions get no tags and the tag filter is AND-only across all viewers including the submitter. This doesn't break the "add it to your list immediately" flow (`upsertMyList` doesn't re-check tags on entities already being added directly), it only affects re-searching for it afterward. Documented here rather than fixed — the real fix (auto-apply the category's required tags to a submission made from that category, which needs `categorySlug` added to `EntitySubmissionInput`) is a small but real scope addition.

**Environment note:** port 3001 is occupied by an unrelated project (`create-coin`) on this dev machine — the server runs on **3002** here (`PORT` in `.env`, `EXPO_PUBLIC_API_URL` in `apps/mobile/.env`). `packages/db/prisma/.env` is a symlink to the root `.env` — Prisma CLI only auto-loads `.env` from next to `schema.prisma`, not the monorepo root, so without this symlink `db:push`/`db:seed` fail with "Environment variable not found: DATABASE_URL".

## Safety / Media / Auth-Completion — Backend Build + Live Verification

Added three backend tracks the user explicitly approved (safety baseline, photo upload, auth completion) — schema → spec → SDK → server, then live-verified every path over real HTTP against the running MariaDB instance (not just typechecked):

- **Safety:** block (mutual 404 on profile view, 403 on further messaging, excluded from discovery), unblock, report (profile or message) — all confirmed live with alice/carol/bob.
- **Media:** multipart upload → local disk storage → served back over HTTP → attached to a profile's `avatarUrl`/`photos` via the existing `PATCH /profiles/me` → deletion — full round trip confirmed live.
- **Auth completion:** register → `isVerified: false` → send-verification → OTP logged by the email stub → verify-email → `isVerified: true`; forgot-password → OTP logged → reset-password → old password rejected, new password works, **all prior sessions invalidated** — all confirmed live, including the security edge cases (no email enumeration on forgot-password, wrong code rejected, single-use code can't be replayed).

**Bugs found and fixed via this live testing** (again, none caught by typecheck — only real requests surfaced them):
1. `fastify-openapi-glue` validates `request.body` against whatever JSON Schema the spec's `requestBody` declares — but `@fastify/multipart` never populates `request.body` (files are consumed via the streaming `request.file()` API), so *any* declared schema for `/media/upload`, even an empty `{}`, made ajv reject every real upload as "must be object". Fixed by not declaring a `requestBody` schema for that one operation at all (documented via the `description` field instead) — `MediaService` already does the real file-type/size validation.
2. `User` never exposed `isVerified` in the API response (`serializeUser` + the OpenAPI schema both omitted it) even though the DB flag was being set correctly — the verify-email flow "worked" but the client had no way to observe the result. Added it to both.

**Process-management gotcha hit repeatedly this session, worth knowing:** backgrounding `pnpm --filter server dev` with `(... &)` and then relaunching after an edit does **not** reliably kill the previous `tsx watch` process in this sandbox — `pkill -f "tsx watch src/index.ts"` silently failed to match multiple times, leaving up to *four* stale server processes racing on `EADDRINUSE` simultaneously, one of which was still serving requests from before dependencies were even installed. This produced a very confusing "bug" (persistent validation error that no code change could fix) that turned out to be a zombie process, not application code. **Before trusting any live-test result against this server, confirm exactly one process holds port 3002** (`ss -ltnp | grep 3002`, cross-check the PID) — don't just check that `/health` responds.

**Mobile UI does not use any of the three new tracks yet** — see the "backend only" notes in Modules Built. That's the natural next step but wasn't part of what was asked for this round.
