# Shared Content System Proposal

**Datememe organizes semantic content units into meaningful collections. The frontend presents those collections through four reusable structures—Grid, Rail, Spotlight, and River—while interactive experiences such as Quick Picks remain independent feed modules. Interruptions are optional and sparse. The feed must remain valid if every interruption is absent.**

## 1. Overview and Rationale

Currently, Datememe's primary engagement surfaces—Favorites and Discover—are implemented as siloed, purpose-built screens. Continuing to build purpose-specific cards (`FavoriteCard`, `MatchCard`, `PollCard`) will result in UI inconsistency and massive frontend debt.

**The Core Principle:** Content identity is decoupled from presentation. The backend decides *what* collection is meaningful, and the frontend decides *how* that collection looks. If the backend owns the final presentation model, visual redesigns turn into backend work.

### Architecture at a glance

```
PAGE CHROME
  PageSummary
  FilterChips

DOMAIN
  ContentUnit
  ContentCollection
    - semantic type
    - context
    - suggestedStructure
    - cacheability / enrichment strategy

PRESENTATION
  Grid · Rail · Spotlight · River
    - each has render budgets
    - each has loading/empty/error contracts

INTERACTIVE MODULES
  Quick Picks
  other non-collection experiences

COMPUTATION
  Global precomputed metrics
  + viewer-specific enrichment
```

`PAGE CHROME` and `COMPUTATION` are new relative to the original three-domain split — a page's own personal-summary header isn't a content collection (§3), and metrics have different runtime costs that the domain layer needs to be explicit about (§6).

### Core invariants

These three rules are load-bearing for everything below them — later sections assume them rather than re-argue them:

- **Interruptions are optional and sparse.** If there isn't a strong insight, the system omits it rather than manufacturing filler. The baseline stream must remain valid and complete with every interruption absent (elaborated in §2).
- **`suggestedStructure` is advisory, never authoritative.** The backend may hint at a preferred layout; the frontend always has final say per viewport/context (§5).
- **The semantic payload may be richer than the visual treatment.** Layout structures are responsible for selecting which information to reveal, not for forcing the backend to reshape content differently per surface (§5, render budgets).

## 2. Dominant Grammar vs. Interruptions

A crucial architectural shift is how we think about a "Page".

**Old Model:** A page is an ordered set of named, static sections. This feels like a rigid dashboard.
**New Model:** A page consists of a **dominant content grammar** (e.g., Favorites or People) that is occasionally **interrupted by specialized modules**. Taxonomy and filtering (Chips) sit at the top to steer the feed, but they don't replace the feed.

- **The Baseline:** The primary content stream relies on the **Grid** as the default visual treatment. We will rely on imagery and typography to define objects, moving away from heavy bordered gray cards. This baseline content continues indefinitely between interruptions.
- **The Interruptions:** Collections mapped to `Rail`, `Spotlight`, and `River` modules act as contextual shelves that break up the baseline stream to inject discovery or insights.

These interruptions should be highly contextual and dynamically generated by the backend (e.g., *"Because you ranked Alien #1"*), rather than static categories. Most importantly, **interruptions are optional and sparse**. If there isn't a strong insight, the system omits it rather than manufacturing filler, and the baseline grid simply continues uninterrupted.

## 3. Page Chrome vs. Feed

Not everything on a page is a `ContentCollection`. A page's own personal-summary header — completion counts, a progress bar, a featured pick — describes the *viewer*, not a browsable set of items. Forcing it into `Spotlight` ("one primary content unit") is a category error: there's no unit, just the viewer's own aggregate state.

`PageSummary` is chrome, rendered once, outside the `FeedModule` stream:

```typescript
type SummaryStat = {
  label: string
  value: string | number
}

type PageSummary = {
  title: string
  subtitle?: string

  stats?: SummaryStat[]

  progress?: {
    value: number
    max: number
  }

  featuredEntity?: Entity
}

type ContentFeedPage = {
  summary?: PageSummary
  chips?: FilterChip[]
  modules: FeedModule[]
}
```

So Favorites/Lists can render:

> **Lists** — 42 favorites · 8 completed lists · 67% profile depth — Featured pick: Alien

as a `PageSummary`, without pretending it's a `Spotlight`. `Spotlight` stays a real feed structure, reserved for an actual promoted `ContentUnit` (§7).

## 4. The Three-Layer Architecture

### Layer 1: Domain / Backend Data
The content unit is the foundational building block. Metrics, capabilities, and social context are properties of units. Rather than dictating UI actions, the backend exposes capabilities (state) which the frontend renders as appropriate buttons (Add, Rank yours, View profile). The backend groups these units into semantic collections via scalable types.

```typescript
type MetricType =
  | 'popularity'
  | 'community-position'
  | 'viewer-position'
  | 'percentile'
  | 'overlap'
  | 'rarity'
  | 'trend'
  | 'completion'

type Metric = {
  type: MetricType
  label: string
  value: string | number
  // Render-priority hint, not a domain fact — see §5 (render budgets).
  importance?: 'primary' | 'secondary' | 'tertiary'
}

type Capabilities = {
  canFavorite?: boolean
  canRank?: boolean
  canMessage?: boolean
  canOpenProfile?: boolean
}

type ContentUnitKind = 'poll' | 'person' | 'category' | 'entity' | 'insight'

type ContentUnit = {
  id: string
  kind: ContentUnitKind
  title: string
  subtitle?: string
  media?: ContentMedia
  metrics?: Metric[]
  badges?: Badge[]

  // Backend defines state; Frontend decides the CTA
  capabilities?: Capabilities

  // Position of this unit *within the current collection* — the only
  // ordering field on ContentUnit. Any comparative ranking (community
  // standing, the viewer's own placement, percentile, etc.) is a fact
  // about the unit, not its position, and belongs in `metrics` as
  // 'community-position' / 'viewer-position' / 'percentile'. One field
  // for order, one channel for every other kind of rank — not three.
  position?: number

  relationship?: { favorited?: boolean; completed?: boolean }

  // Reuses the canonical Entity shape already serialized elsewhere in the
  // API (imageUrl, canonicalName, usageCount, ...) instead of a parallel,
  // simplified entity type. EntityType in this system is a dynamic table,
  // not a fixed enum, so a hardcoded `type: 'artist' | 'movie' | ...` here
  // would drift from it immediately.
  entity?: Entity
}

type CollectionType = 'favorites' | 'lists' | 'recommendations' | 'comparison' | 'trending' | 'prompt'

type ContentCollection = {
  id: string
  type: CollectionType
  title?: string
  context?: {
    reason?: string
    sourceEntityId?: string
    sourceEntityType?: string
  }
  // A hint, not a mandate — see the "suggestedStructure" invariant in §1.
  suggestedStructure?: 'grid' | 'rail' | 'spotlight' | 'river'
  items: ContentUnit[]
}
```

*(e.g., `Because you like` or `Similar taste` become recommendation strategies handled by the `context` block, rather than permanent top-level ontology).*

**Collection context vs. unit metrics — both altitudes, together:**

```typescript
{
  id: 'because-alien',
  type: 'recommendations',
  title: 'Because you ranked Alien #1',
  context: {
    sourceEntityId: 'alien',
    reason: 'You ranked Alien #1',
  },
  suggestedStructure: 'rail',
  items: [
    {
      kind: 'person',
      title: 'Alex',
      metrics: [
        { type: 'overlap', label: 'Shared movie taste', value: '82%', importance: 'primary' },
        { type: 'viewer-position', label: 'Alien', value: 1, importance: 'secondary' },
      ],
    },
  ],
}
```

`context` answers *why this shelf exists*; `metrics` answer *why this item is interesting*. Keep them at their own altitude — don't collapse a collection-level rationale into a unit-level fact or vice versa.

### Layer 2: Frontend Composition
The frontend receives feed modules (either a collection or a special interactive module like Quick Picks). It maps semantic collections to visual sections, using `suggestedStructure` as a default rather than a hardcoded `type -> structure` lookup table — that table would just relocate the rigidity the whole system exists to remove.

```typescript
type ContentSection = {
  id: string
  title?: string
  subtitle?: string
  structure: 'spotlight' | 'rail' | 'grid' | 'river'
  items: ContentUnit[]
  options?: { gridShape?: 'square' | 'dense' }
}

type InteractiveModule = {
  id: string
  kind: 'quick-picks'
}

type FeedModule = ContentCollection | InteractiveModule
```

### Layer 3: Page-level Composition
A `ContentFeedPage` (§3) wraps an optional `PageSummary`, optional `FilterChip[]`, and the `FeedModule[]` stream. The dominant grammar streams continuously through `modules`, punctuated by curated interruptions; the summary and chips render once, above it.

## 5. The Four Layout Structures

1. **Grid** (Square or Compact / Matrix)
   - A multi-column field of square or dense units. This is the default visual treatment for the dominant grammar.
2. **Rail** (Portrait / Horizontal)
   - A horizontal stream of portrait/mobile-proportioned units.
   - Best used as an interruption for highly browseable, related sub-collections.
3. **Spotlight** (Wide / Two-column)
   - A large two-column feature containing *one primary content unit*.
   - A heavy, conditional interruption meant to draw immediate focus (e.g., a major taste insight). If there is no strong candidate, it is omitted entirely.
4. **River** (Wide / Vertical)
   - A vertically flowing stream of full-width information units.
   - Ideal for rankings, activity, and deep community context.

### Render budgets

A unit may carry more semantic data (metrics, badges) than a given structure has room for. **Structure renderers select by priority (via `Metric.importance`); they do not dump all available fields.** Concretely:

| Structure | Metrics | Badges | Subtitle | Actions |
|---|---|---|---|---|
| Grid / dense | 1 (primary) | 1 max | none | 1 primary |
| Grid / square | 1 | 1 | short | 1 primary |
| Rail | 2 max | 1 | short | 1 |
| Spotlight | 3 max | 2 | rich | primary + secondary |
| River | 3–5 | multiple | rich, with context | multiple |

This is a floor for implementation, not a final spec — but every structure component should be built against *some* explicit budget from day one, not left to grow organically per call site.

## 6. Metric Computation & Caching Contract

`popularityCount`, `topPick`, and `matchAnswerMultiplier` — three metrics already shipping in the Lists redesign — have three different runtime characteristics, and the domain model needs to say so explicitly or the caching question never gets answered:

- **`popularityCount`** → precomputed on write, via a worker job → globally cacheable.
- **`topPick`** → precomputed on write, via the same worker job → globally cacheable.
- **`matchAnswerMultiplier`** → viewer-specific → resolved per viewer, at request time or via a viewer-scoped cache → **never** globally cacheable.

**Rule:** Collection responses may combine globally cacheable metrics and viewer-specific metrics. Global metrics should be precomputed where practical; viewer-specific metrics are resolved at request time or through viewer-scoped caches — never baked into a shared cache entry.

This implies a two-step resolution pattern rather than one monolithic query:

```
collection base        (cached globally, keyed by collection id)
  +
viewer enrichment       (attached after base retrieval, keyed by viewer id)
```

Internally, a resolver can track *why* a metric was cheap or expensive to produce (precomputed vs. resolved live vs. hybrid) to decide caching strategy — but that provenance is a backend/resolver-layer concept, not a client-facing field. There's no UI that needs to know a metric's `source`; exposing it on the wire `Metric` type would leak an implementation detail with no consumer. Keep `Metric` (§4) client-facing and clean; keep source-tracking internal to the resolver.

## 7. Rendering Contracts: Loading, Empty, and Error States

Each structure needs an explicit state contract, not an implicit one discovered per component:

```typescript
type StructureState = 'loading' | 'ready' | 'empty' | 'error'
```

Phase 1 (§9) should deliver, per structure:

- **Grid** — real layout, matching skeleton, empty state, error state.
- **Rail** — real layout, matching skeleton, empty state, error state.
- **Spotlight** — real layout, matching skeleton, empty/omit behavior (per the "optional and sparse" invariant, §1), error behavior.
- **River** — real layout, matching skeleton, empty state, error state.

**The skeleton must preserve the real layout's aspect ratio, line count, spacing, media position, and card geometry.** A skeleton that only approximates its real component's shape is a recurring, avoidable source of visual-mismatch bugs — worth locking as a hard requirement, not a nice-to-have.

## 8. Page Re-imagining

Taxonomy chips at the top of pages must be strictly semantic dimensions to avoid mixing axes. The dominant grammar explicitly returns and continues after every interruption.

### The New "Lists" (formerly Favorites)
- **[ PAGE SUMMARY ]**: 42 favorites · 8 completed lists · 67% profile depth · Featured pick: Alien
- **[ CHIPS ]**: All | Music | Movies | TV | Books | Games | Food
- **[ GRID ]**: YOUR LISTS (Baseline grammar)
- **[ RAIL ]**: ADD MORE (Interruption: Unanswered relevant prompts)
- **[ GRID ]**: YOUR LISTS (Baseline continues)
- **[ SPOTLIGHT ]**: TASTE SPOTLIGHT (Conditional Interruption)
- **[ GRID ]**: YOUR LISTS (Baseline continues)
- **[ RIVER ]**: HOW YOU COMPARE (Interruption: Detailed comparison stories)
- *(...Baseline continues infinitely)*

### The New "Discover"
Discover shifts from being *only* a swipe deck to a rich content feed where *People* are the baseline grammar.

- **[ CHIPS ]**: For You | New
- **[ GRID ]**: PEOPLE (Baseline grammar)
- **[ RAIL ]**: BECAUSE YOU RANKED ALIEN #1 (Contextual Recommendation Interruption)
- **[ GRID ]**: PEOPLE (Baseline continues)
- **[ INTERACTIVE MODULE ]**: QUICK PICKS (The swipe experience module)
- **[ GRID ]**: PEOPLE (Baseline continues)
- **[ RAIL ]**: SIMILAR TASTE (Interruption)
- **[ GRID ]**: PEOPLE (Baseline continues)
- **[ SPOTLIGHT ]**: HIGHLY COMPATIBLE (Conditional Interruption)
- *(...Baseline continues infinitely)*

### Pressure-testing against the Lists page already shipped

Before committing further abstraction work, the model should be checked against real, already-built components — not just new mockups. Mapping what's live today:

| Shipped today | Becomes |
|---|---|
| `TasteProfileHero` | `PageSummary` — not a feed module (§3) |
| `CompletedListsGrid` | `ContentCollection(type='lists')`, `suggestedStructure='grid'` |
| "Answer these next" (`CategoryStatCard` grid) | `ContentCollection(type='prompt')`, `suggestedStructure='grid'` or `'rail'` — each unit carries `popularity`, a `topPick` entity, and (when present) a viewer-specific match-answer metric |
| "More to explore" (`CategoryDiscoveryCard` grid) | `ContentCollection(type='prompt')`, `suggestedStructure='grid'`, dense render budget |
| Single strongest unanswered list | Optional promoted collection, `suggestedStructure='spotlight'` |

This mapping is clean, which is itself the validation: nothing needed a fifth structure or an escape hatch, once `PageSummary` was split out. It also answers the migration question directly — **`CategoryStatCard` and `CategoryDiscoveryCard` don't get discarded, they become rendering variants of `ContentUnit`**, and `CompletedListsGrid` becomes a `GridSection` plus a unit renderer for list-shaped entities. Phase 3 (§10) should say *migrate/remap*, not *replace*.

## 9. Technical Implementation & Scale

### Feed Loading and Pagination
The system will utilize two independent pagination models:

1. **Initial Feed Request**: Returns enough modules for the first meaningful viewport(s).
2. **Feed Pagination**: Uses an intersection observer on the feed level.
   - `GET /discover/feed?cursor=x`
3. **Collection Pagination**: Explicit "View all" functionality within a specific section.
   - `GET /discover/collections/:collectionId?cursor=x`

## 10. Recommended Next Steps

1. **Phase 1: Data Contracts & Component Primitives**
   - Finalize the `ContentUnit`, `ContentCollection`, and `PageSummary` backend API schemas (§3, §4).
   - Build the base `ContentUnit` renderer and the generic `Metric` types, including `importance`-based field selection (§5).
   - Build the four structure containers (`Spotlight`, `Rail`, `Grid`, `River`), each with its render budget (§5) and its loading/empty/error contract with a layout-matched skeleton (§7).
2. **Phase 2: Backend Feed Adapters**
   - Implement backend endpoints to supply the semantic structures.
   - Implement the global-cache-plus-viewer-enrichment resolution pattern (§6) rather than one monolithic per-request query.
3. **Phase 3: Page Migration**
   - Migrate/remap `CategoriesScreen.tsx` (Lists) onto the new model, per the mapping validated in §8 — not a ground-up replacement.
   - Migrate/remap `DiscoveryScreen.tsx` onto the new Discover feed.
