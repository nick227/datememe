# AI content factory: V1 implementation spec

Status: agreed scope translated into an implementation spec. Documentation only; the features below are not implemented yet.

**V1 proves a simple bulk poll pipeline. Concepts create content; taxonomy organizes content; Lists are polls; Entities are shared values.** Concept is a cheap authoring object, never a public taxonomy node. This specification supersedes the earlier proposal to merge Concept and taxonomy.

## 1. Bulk workflow

```text
AI generates concepts → CONCEPT INBOX
→ use / skip selected concepts
→ generate ~10 Lists per selected concept
→ approve / edit Lists
→ assign existing taxonomy per List
→ generate Values for ready Lists
→ resolve / approve Values
→ publish ready Lists locally
```

AI can generate concepts such as `coffee`, `punk`, `space`, `dating`, `travel`, and `nostalgia` without fitting them into a hierarchy. Admins select concepts in bulk; they do not configure individual concept pages.

For example, `coffee` might produce “Favorite Coffee Chains,” assigned to the existing food group and coffee-chain value type. `space` might produce “Favorite Space Movies,” “Best Space Games,” and “Favorite Space Books.” Each poll receives its own appropriate group/type. One creative seed can cross several permanent site branches.

Keep all generated material in drafts until reviewed. Approval of a List definition is separate from taxonomy assignment; both are required before generating its Values. Publication requires accepted, resolved values. User `List`/`ListItem` answers are never generated by this pipeline.

Use **List** in the existing admin vocabulary and make clear it means a poll definition (`Category` in storage). Ten List ideas create ten draft definitions, not ten EntityTypes.

## 2. Five new models

### Concept

Only four fields are needed:

| Field | Purpose |
| --- | --- |
| `id` | Internal identity |
| `key` (unique) | Normalized deduplication key, generated automatically |
| `label` | Creative seed text, such as “space” |
| `status` | `NEW`, `USE`, or `SKIP` |

No thumbnail, public slug editor, hierarchy, metadata, taxonomy assignment, or concept-detail settings screen. `key` is an internal deduplication key, not a public route. Normalize whitespace/case consistently; exact repeats reuse the existing Concept and preserve the admin's use/skip decision. Related ideas can coexist; no semantic concept ontology is needed.

Concepts have no EntityType or CategoryGroup foreign key. `CategoryDraft.conceptId` retains the authoring source. Do not add `Category.conceptId` or expose concepts through public browsing/matching APIs. The existing draft-to-published-category link is enough to trace where content came from.

The remaining four models have IDs/timestamps. Use existing User references for operator attribution where needed. No extra campaign, revision, or prompt-registry models.

### GenerationOperation

| Field | Purpose |
| --- | --- |
| `kind` | `CONCEPTS`, `LIST_IDEAS`, `VALUES`, or `FACETS` |
| `conceptId`, `categoryDraftId`, `entityId` (nullable, as applicable) | Source concept, draft, or entity; concept-batch generation has no single target |
| `input` (JSON) | Batch brief, target context, exclusions, requested count, and input hash |
| `model`, `systemPrompt`, `userPrompt`, `promptVersion` | Model and exact rendered prompts used |
| `status` | `PENDING`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELED` |
| `output` (JSON, optional), `error` (optional) | Returned proposals or failure reason |
| `requestedByUserId`, `completedAt` | Operator and completion |

This is enough provenance for V1. No separate attempts, pricing ledger, prompt registry, or provenance graph. A retry creates a new operation; previous output remains inspectable. Persist proposals and mark success together so success means the draft output exists.

### CategoryDraft

| Field | Purpose |
| --- | --- |
| `conceptId`, `generationOperationId` | Creative seed and generation source |
| `title`, `slug`, `prompt` | Proposed list definition |
| `entityTypeId`, `groupId` (initially nullable), `parentEntityId` (optional) | Permanent structure assigned per List after idea review |
| `rules` (validated JSON) | Min/max answers, ranked/unranked mode, supported eligibility constraints |
| `approvalState` | `DRAFT`, `APPROVED`, `REJECTED` |
| `publishedCategoryId` (nullable, unique) | Existing Category after first publication |

An idea can be reviewed before its taxonomy is assigned. Require a valid existing group and value type before value generation/publication; do not derive them from Concept. Reuse existing taxonomy selectors and allow batch assignment to compatible Lists. AI may suggest assignments, but cannot create/reparent taxonomy nodes. If no suitable type exists, leave the List unassigned for later rather than expanding this pipeline into taxonomy management.

A published draft stays linked to its Category and serves as the workspace for more candidates. No snapshots, branching, superseded revisions, or separate publication-state machine.

Before publication, editing an approved definition returns it to DRAFT. Revalidate existing candidates if its type or rules change. After publication, lock definition fields in this V1 workflow; expansion adds values only. Editing published definitions can continue through existing administration until a later dedicated workflow is designed.

### EntityCandidate

| Field | Purpose |
| --- | --- |
| `categoryDraftId`, `generationOperationId` | Destination and source |
| `name`, `details` (JSON) | Proposed name and disambiguators, such as year/creator |
| `resolutionState` | `UNRESOLVED`, `EXISTING`, `NEW`, `AMBIGUOUS` |
| `resolvedEntityId` (nullable) | Shared Entity when known/materialized |
| `reviewState` | `PENDING`, `APPROVED`, `REJECTED` |

Resolution and acceptance are separate: a correctly identified entity can still be unsuitable for a particular list. NEW means the admin has reviewed it as a new identity, not that an Entity has already been inserted.

Candidate mentions can repeat across lists. **Published entities must be shared.** Repeated candidate suggestions are filtered or rejected and do not count as additional values.

### EntityFacet

| Field | Purpose |
| --- | --- |
| `entityId` | Shared owner |
| `axis`, `value` | For example `tone:dark`, `theme:isolation`, or `genre:science-fiction` |
| `source` | `ADMIN`, `AI`, or `API` |
| `generationOperationId` (optional), `sourceUrl` (optional) | Lightweight source reference |

Unique key: `(entityId, axis, value)`, using normalized axis/value strings. Store only accepted facets here; AI suggestions remain in GenerationOperation output until accepted. Existing facets remain when another generation runs. Admins can remove or correct facets directly.

Use a small vocabulary defined in code for the first axes. Do not add FacetDefinition or assertion-history tables. Factual fields such as year and creator can remain in existing `Entity.metadata`; use verified sources or manual entries and leave unknown facts empty. Prefer factual APIs when available, but a new provider-ingestion system is not required to complete the first pilot.

## 3. Shared entity resolution

Use existing Entity, EntityAlias, EntityExternalRef, and `(entityTypeId, slug)` uniqueness. No separate identity registry.

The review screen offers three actions: **Use existing**, **Approve as new**, and **Reject**. It shows matching names/aliases within the type plus disambiguating details. Verified external IDs are stronger evidence than names; ambiguous matches always require a decision. Do not auto-merge using AI confidence or a name-derived slug alone.

Examples:

- Alien (1979 film) in three categories links to one Entity.
- Another work named Alien is not automatically the same entity.
- Radiohead in multiple genre/decade lists links to the existing artist.

On publication, recheck NEW candidates against current entities. Insert a reviewed disambiguated slug only when there is no identity conflict. The database constraint handles concurrent same-key creation; a collision must be resolved or reported, never silently treated as proof of identity. Candidates representing the same new work within the publication resolve to one Entity. Later publications search/reuse that row.

If external IDs are supplied, verify them and check for multiple existing claims; the current provider/external-ID index is not unique. Ambiguities block those candidates. V1 relies on admin review plus database key protection; it does not promise automatic semantic deduplication of every possible title variation.

## 4. Publishing and expanding locally

The initial Publish action validates the approved definition and selected approved candidates, then uses one short database transaction to:

1. Resolve/create the selected shared Entities.
2. Create the Category with its existing taxonomy scope and validated configuration.
3. Insert CategoryEntity relationships.
4. Set candidate entity references and `publishedCategoryId`.

A repeated publication uses the existing linked Category. Unique category/entity relationship keys make reapplying the same accepted values a no-op. A failed transaction leaves no partial category or new entities. AI calls happen before this transaction.

Unresolved or ambiguous candidates cannot be selected for publication. Unselected pending/rejected candidates need not block a useful list. Require enough accepted values to satisfy the definition and its displayed promise: a “top five” list needs at least five usable choices.

For **Expand values**, generate suggestions with current choices and previously rejected candidates as exclusions. Review and resolve them through the same screen. “Add approved values” inserts only new CategoryEntity relationships; it does not replace existing choices, delete entities, modify metadata, or touch user answers. Report actual net additions rather than promising the requested count.

Generated V1 lists use an explicit curated pool. Add a small `poolMode` field to Category with a default preserving existing behavior, and set new generated categories to `CURATED`. Apply the curated allowlist consistently in autocomplete, list saving, and category-specific Quick Picks. This is required for the generated lists to work; it is not a broader taxonomy redesign. Reject unsupported rules in the draft validator.

Draft definitions and NEW candidates stay in the authoring models until publication. Do not create inactive public Categories or abuse Entity moderation status as a draft flag.

## 5. Simple bulk execution and developer prompts

Reuse OpenAIService and existing admin authentication, review components, and audit conventions. Implement four typed generation methods: concepts, List ideas, Values, and optional facets. Validate all output server-side; malformed output is a failed operation, never accepted catalog data.

### Developer-owned prompt files

Keep prompts as plain files beside the server integration; proposed layout:

```text
apps/server/src/prompts/catalog/
  concepts.system.md
  concepts.user.md
  lists.system.md
  lists.user.md
  values.system.md
  values.user.md
  facets.system.md
  facets.user.md
  config.ts
```

`config.ts` holds per-stage model, prompt version, default count, maximum count, and timeout. Start with approximately 50 concepts per request, 10 Lists per concept, and 20 Values per List; these are tunable defaults, not database rules. Use the existing configured model initially.

System templates define the role, quality bar, and output contract. User templates contain a few named placeholders:

| Stage | Inputs to the user template |
| --- | --- |
| Concepts | `brief`, `count`, `existingConceptKeys` |
| Lists | `conceptLabel`, `brief`, `count`, `existingListTitles` |
| Values | `listTitle`, `listPrompt`, `entityType`, `rules`, `count`, `existingValues`, `rejectedValues` |
| Facets | `entityName`, `verifiedFacts`, `allowedFacets` |

A Lists user template can simply start with: “Suggest {{count}} distinct polls inspired by {{conceptLabel}}. Brief: {{brief}}. Avoid these existing titles: {{existingListTitles}}.” Keep taxonomy out of this stage's creative constraints. Value generation uses the subsequently assigned type/rules.

Use simple literal placeholder substitution, with no executable template expressions. Output schemas live in typed code and are validated independently of prompt text. A developer should be able to change wording in a Markdown file and count/model settings in one config file without touching handlers or schema. Include those files in the server build, with paths verified in the compiled app. Record rendered prompts and their version in GenerationOperation; a local preview command prints rendered prompts without calling AI. No prompt editor UI or prompt-management service.

### Bulk actions without a new orchestration platform

Each bulk action creates a bounded set of GenerationOperations: one concept-generation operation per chunk, one List-idea operation per selected concept, and one Values operation per ready List. Generation must not be a giant request containing the entire content tree.

For local V1, use a single admin-driven executor: the UI calls a server endpoint to execute one pending operation at a time, then advances through the batch. Persist the pending operation IDs and outputs; refresh can list pending/failed operations and resume by explicit action. Atomically claim PENDING → RUNNING so double clicks cannot execute the same operation twice. Each call has a finite timeout. If interrupted, show the operation as stale and allow explicit failure/retry; accept a result only while that operation is still RUNNING. Retry creates a new operation. Snapshot draft input in the operation and discard results if the definition/type changed before completion.

Show completed/failed/pending counts and actual generated counts. One failed concept or List does not stop independent items. Stop cancels pending work; completed proposals remain for review. Page closure may stop further dispatch, which is acceptable for this local POC and should be clear in the UI. Background completion, automatic recovery, worker routing, and queue fencing are deferred.

Each review stage is an explicit bulk action, not an automatic cascade to publication. Shared identity conflicts still require individual decisions. Publication runs one transaction per List, so one blocked List does not prevent other ready Lists from publishing.

### Admin interface

The primary entry is **Content → Concept Inbox**:

- **Concept Inbox:** Generate concepts, select many, Use, Skip, Generate Lists. Show label, use/skip state, and generated List count. Allow simple manual entry as a fallback. No hierarchy browser or per-concept configuration.
- **List review:** batch view of proposed titles/prompts with source concept; approve/edit/reject, assign existing group/type, then Generate Values for ready rows. Show blockers such as “Needs value type.”
- **Value review:** generated options grouped by List, shared-entity matches, approval actions, and Publish ready Lists. Later use the same view to expand existing Lists.

Facets remain a small optional action on existing entity detail, not a gate for completing every poll. Existing taxonomy screens/settings remain unchanged during V1. Redesigning or moving those screens is outside this build. The pipeline uses taxonomy only when a List needs its permanent assignment.

## 6. Implementation order and acceptance

Build against the local development database first. The first complete demonstration is:

**Generate 50 concepts → use 3 (including space) → generate 10 Lists each → approve 3 spanning movies/games/books → assign taxonomy per List → generate 20 Values each → resolve/approve → publish locally → expand one List by up to 10 net-new values.**

Verify the EntityFacet model separately by accepting a few reusable facets; it does not gate this core content-factory demonstration.

| Step | Deliverable | Done when |
| --- | --- | --- |
| 1 | Five models and Concept Inbox/List review | Refresh preserves drafts and approval decisions |
| 2 | Prompt files, four generation methods, and bulk operation execution | Developers can preview/tune prompts; batch progress survives refresh; individual failures can be retried |
| 3 | Candidate review and shared resolution | The same film in multiple lists resolves to one Entity; ambiguous identities require review |
| 4 | Transactional local publish and curated eligibility | Generated lists work in the existing List builder; draft content is absent from public APIs |
| 5 | Entity facets and additive expansion | Facets belong to shared entities; expansion preserves all existing relationships and user answers |

Focused checks:

- AI-generated concepts require only key/label/status, with bulk use/skip; repeated concept generation preserves existing decisions.
- One concept produces Lists assigned to different existing taxonomy types; no public Concept field or automatic taxonomy mutation is introduced.
- Approval can precede assignment, but unassigned Lists cannot generate Values or publish.
- Changing a prompt file changes the rendered request without editing pipeline code; operations retain the exact prompts used.
- A failed item does not stop the rest of a batch; resuming pending operations does not regenerate completed results.
- Rejected definitions cannot generate values; unapproved content cannot publish.
- Alien reused across three lists produces one Entity and three relationships; a same-name different work remains distinguishable.
- Repeating publish/add-values does not duplicate categories, entities, or relationships.
- An injected publication failure rolls back the whole small publication transaction.
- An interrupted/invalid AI response cannot be mistaken for accepted catalog data.
- Accepted facets are reusable from every list containing that entity; regenerating suggestions does not erase them.
- Curated choices agree between search, saving answers, and Quick Picks.
- Generating, publishing, and expanding do not write User, List, ListItem, or matching-score records.

V1 is complete when an admin can perform this workflow end to end in the local app. Running more creative concept batches through the same flow is the next content exercise, not a requirement to build multiple factual provider adapters first.

## 7. Explicitly deferred

- Generic revisions, branching, immutable authoring snapshots, identity registries, facet assertion histories, and detailed provenance graphs.
- Taxonomy redesign, public concept browsing, per-concept settings, and hierarchy controls in the generation pipeline.
- Dedicated authoring infrastructure, generation queues/workers, fencing, automatic retries/recovery, and campaign budgets. Explicit resumption of pending bulk operations is in V1.
- Matching weights, facet similarity, embeddings, shadow scoring, or changes to existing matchmaking. Store useful facets now; evaluate their use later.
- Automated factual ingestion across multiple providers, media generation/import, and autonomous publication.
- Release bundles, import ledgers, staging promotion, and production seeding automation as V1 implementation requirements.

The existing [seeding analysis](seeding-analysis-and-proposal.md) remains the infrastructure research and future promotion plan. JSON bundles remain the intended production transport once the content factory works. V1's Publish button explicitly targets the **local catalog**; it does not authorize or implement production promotion. Before using this workflow on Railway production, return to the documented schema, identity, import, and persistence requirements.
